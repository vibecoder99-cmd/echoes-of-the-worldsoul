## D. C++ / Playerbots audit

Source of truth: `E2J13-PLAYERBOTS-INTEGRATION-BOUNDARY.md` (2026-08-14,
direct source inspection) and `E2J13-SERVER-COMPONENT-MANIFEST.md`,
cross-checked against the current 3-module directory listing.

**`mod-echoes-playerbots`** — the Playerbots bridge. Public
`cpp_patch/mod_attunement_plus.patch` (a single-file diff creating
`modules/mod-attunement-plus/`, one `.cpp` file, zero Playerbots
awareness) is entirely superseded — proven, not assumed: the current
module has ~14 source files (`EchoesActionBridge`, `EchoesAdapterFactory`,
`EchoesAwareness`, `EchoesBotActionTypes`, `EchoesBotCache`,
`EchoesConfig`, `EchoesDisposition`, `EchoesDissolutionAdapter/Policy`,
`EchoesForgeAdapter`, `EchoesHooks`, `EchoesPresence`, `EchoesProtection`,
`EchoesRackAdapter`, loader) plus 8 C++ test files and 1 Python contract
test, under a renamed module directory the old patch never mentions.

**Load-bearing caveat, not previously documented anywhere in the public
repo**: `E2J13-PLAYERBOTS-INTEGRATION-BOUNDARY.md` proved this module has
a **hard, unguarded compile-time dependency** on `mod-playerbots` —
unconditional `#include "RandomPlayerbotMgr.h"` / `#include "Playerbots.h"`,
zero `#ifdef`/`MOD_PLAYERBOTS` guards anywhere in its source, and the
module-source-globbing build logic never excludes it. **A server owner
without `mod-playerbots` present will get an outright build failure if
`mod-echoes-playerbots`'s directory is included in their build tree at
all** — not a graceful runtime no-op, despite the module's own README
claiming "fail-dormant" behavior (that claim is only true when Playerbots
is present-but-disabled, not when it's physically absent from the source
tree). This is a real, confirmed, currently-buildable defect, not
supersedes-the-old-patch trivia — it must be represented accurately in
whatever public installer/documentation ships this module, or public
server owners without Playerbots will hit a broken build. Not fixed here,
per scope — flagged as a hard blocker for **shipping this module as
unconditional public source** until either the installer conditionally
excludes it (per the boundary doc's own stated design implication) or the
module itself gains real `#ifdef` guards (a C++ change, out of this
audit's scope).

**`mod-echoes-stats`** — not present in the public repo at all today.
**Its own committed config comment states: "ISOLATED VALIDATION ONLY as
of E2j3: this module has not been authorized for production deployment."**
Default `Enable=0`. This is a strong, in-source signal that this module
should **not** be synced into the public 2.0 release as a shipped,
enabled feature without a separate, explicit production-authorization
decision — MANUAL REVIEW, not an automatic ADD, regardless of how clean
its Playerbots-independence is (confirmed zero Playerbots headers/symbols).

**`mod-ale`** — required for any Echoes Lua to run at all (Eluna fork),
but it is a substantial third-party project in its own right: its own
`.git` checkout, `README_CN.md`/`README_ES.md`, its own GitHub Actions
workflows, its own LICENSE. Vendoring its full ~30-file source tree
directly into this public repo would blur "what this project owns"
exactly the way `E2J13-TARGET-REPOSITORY-AND-RELEASE-LAYOUT.md` warned
against. Recommend documenting it as a required external dependency
(name, source repository, required version/commit) with installation
instructions, rather than a straight file copy — but this is a
recommendation for the next phase to decide, not something resolved here.

## K. Discovered live bug — tracked, not fixed

**Location**: WSL `env/dist/lua_scripts/ap_forge.lua`, `AP.Forge.Dissolve`'s
`OnForgeDissolve` hook dispatch (interactive gossip dissolve path).

**Current code**: `AP.API.DispatchHook("OnForgeDissolve", { guid=guid,
itemEntry=pending.entry, ... })` — `pending.entry` is always `nil`
(`AP.Forge.Pending` entries only ever set `.itemEntry`, confirmed
elsewhere in the same file: `pending.itemEntry ~= itemEntry`).

**Expected code**: `itemEntry=itemEntry` (the local parameter), exactly
as the second call site in the same file (the direct/API dissolution
path) already does correctly.

**Evidence**: the preserved E2j5h draft
(`docs/e2j5h-evidence/superseded-draft-ap_forge.lua.diff` in this public
repo) contains this exact fix with an explanatory comment, dated
2026-07-25 — the fix was designed over a month ago and never
carried into the current WSL implementation.

**Potential effect**: any consumer of the `OnForgeDissolve` API hook
(currently `AP.API.DispatchHook` — used by `mod-echoes-playerbots`'s
`EchoesHooks.cpp` per the system-implementation map, and any future
integration) receives `itemEntry = nil` for every dissolution triggered
through the normal player-facing gossip menu — the majority path. The
direct/API dissolution path is unaffected.

**Severity recommendation: P1.** Not P0 — no crash, no data loss, no
economy/security exploit (the actual reward grant and database writes
use the correct local `itemEntry`, not `pending.entry`; only the hook's
*notification payload* is wrong). Not P2/P3 either — this silently
breaks a real, currently-shipping public API contract
(`OnForgeDissolve`) for its majority trigger path, which is exactly the
kind of defect that erodes confidence in a hook API once discovered by a
third-party integrator, and Playerbots integration (`mod-echoes-playerbots`)
is a named consumer of this hook surface.

**Not fixed in this audit.** Recommended fix phase: a small, isolated
Lua fix, independent of and prior to the 2.0 component sync (fixing it
in WSL before the sync means the public repo receives the corrected file
directly, rather than syncing the bug forward and fixing it in two
places).

## M. Recommended sync order

Derived from dependency risk, not merely the order requested:

1. **Fix the `pending.entry`/`itemEntry` bug in WSL first** (small,
   isolated, independent of everything else) — so the sync carries the
   correction forward instead of propagating a known bug into the public
   repo and needing a second fix there.
2. **Server Lua export** — the foundation everything else assumes is
   correct; SQL, C++, and Client Companion all reference or depend on the
   current Lua's schema/protocol contracts.
3. **SQL replacement** — depends on #2 being settled (the schema
   reconciliation is Lua-contract-driven, already done in WSL, just needs
   porting).
4. **C++/Playerbots integration export** — depends on #2 (shares
   `ap_botapi.lua`'s status decision) and carries its own compile-time
   caveat that must be resolved (at least documented) before or alongside
   this step, not after.
5. **Client Companion replacement** — depends on #2 (`ap_protocol.lua`
   must already be in place for the AddOn to function against a public
   server built from this same sync).
6. **Config/templates reconciliation** — depends on #2 and #4 being final
   (can't set public defaults for modules that haven't landed yet).
7. **Docs/version metadata** — last, since accurate docs describe the
   end state of everything above, not a moving target.
8. **Installer wiring** — explicitly out of scope for this phase per your
   instruction; follows once 1-7 give it real files to package.
